# تصميم نظام المؤسسة والأقسام — وضوح
> نتيجة تدقيق 2026-09-24 + قرارات المالك. مرجع التنفيذ.

## 1) الموديل (مُعتمد)
- **الحساب الرئيسي (المؤسسي):** طبقة الإدارة والتنسيق والمتابعة والربط — لوحة المؤسسة، رؤية كل الأعمال، إدارة الأقسام والأعضاء. يُفوتر بسعر المؤسسي.
- **الهرمية:** المالك ← ينشئ الأقسام ← يضيف داخل كل قسم مشرفين ← وتحت المشرفين أعضاء.
- **المشرف (مدير قسم):** المالك يختار له: **منتِج (يشتغل)** أو **رقابة/إشراف فقط**.
  - رقابة فقط → **مجاني** (مشمول ضمن الحساب الرئيسي).
  - منتِج → **مقعد احترافي مدفوع**.
- **الأعضاء (تحت المشرفين): دائماً منتِجون = مقعد احترافي مدفوع** لكل عضو (150/شهر + مزايا الاحترافي). لا يوجد عضو عادي مجاني.
- **الفوترة كلها على الحساب الرئيسي.** الفرع لا يُفوتر مباشرة إطلاقاً.
- **الإجمالي = سعر المؤسسي + (كل الأعضاء + المشرفون المنتِجون فقط) × سعر الاحترافي.** المشرفون الرقابيون مجاناً.

## 2) الأدوار
مالك (Owner) ← مشرف (Admin) ← مدير قسم (Dept Manager) ← عضو (Member).
- المالك: كل شيء + الفوترة.
- المشرف: كل شيء عدا الفوترة.
- مدير القسم (المشرف): إدارة أعضاء قسمه ورؤية كل مشاريع قسمه. المالك يحدّد إن كان **منتِجاً (مدفوع)** أو **رقابياً (مجاني، بلا توليد)**.
- العضو: ينشئ مشاريع **داخل قسمه**، يرى مشاريعه + مشاريع قسمه (قراءة) + المشترَك معه. **دائماً منتِج = مقعد مدفوع**.

## 3) مصفوفة الرؤية
| الدور | مشاريعه | قسمه | كل المؤسسة | إدارة أعضاء | الفوترة |
|---|---|---|---|---|---|
| المالك | ✓ | ✓ | ✓ | ✓ | ✓ |
| المشرف | ✓ | ✓ | ✓ | ✓ | ✗ |
| مدير القسم | ✓ | ✓ (قسمه) | ✗ | أعضاء قسمه | ✗ |
| العضو | ✓ | ✓ (قراءة) | ✗ | ✗ | ✗ |
- الفروع لا ترى أعمال بعض إلا في نفس القسم أو عبر مشاركة صريحة.

## 4) الحصص (مُعتمد)
- **عضو منتِج** = 150 مخرجة/شهر مستقلة (مستوى احترافي).
- **مشرف** = لا توليد (حصة 0)؛ رؤية/إدارة فقط حسب دوره.
- تُحسب حسب owner_id للمشروع/المخرج ضمن المؤسسة.

## 5) تغييرات قاعدة البيانات
- `projects`: تعبئة `org_id` + `dept_id` + `owner_id` تلقائياً عند الإنشاء (owner = المنشئ). (الأعمدة org_id/dept_id موجودة؛ يُضاف owner_id إن لزم — حالياً user_id هو المنشئ).
- جدول جديد `project_shares` (project_id, target_user_id أو target_dept_id, permission='read').
- `org_members`: توسيع role ليشمل `dept_manager` (CHECK) + عمود **`can_generate boolean`** (منتِج=مقعد مدفوع / مشرف=مجاني).
- `organizations`: `billed_plan`، وعدّ المقاعد المدفوعة = الأعضاء النشطون الذين `can_generate = true` فقط.
- فهارس على projects(owner_id), project_shares.

## 6) طبقة الصلاحيات والمستوى الفعّال
- `getEffectivePlan(userId)`: عضو مؤسسة نشط **ومنتِج (can_generate)** → professional؛ مشرف → بلا صلاحية توليد؛ وإلا باقته الخاصة. (المالك = enterprise).
- التوليد (`deliverables/generate`, `ai/generate`) محجوب على المشرفين (can_generate=false).
- `canAccessProject(userId, project)`: مالك/مشرف=كل المؤسسة؛ مدير قسم=قسمه؛ عضو=ملكه/قسمه/المشترَك.
- تُستبدل كل قراءات `subscription_plan` الخام و`eq(user_id)` الخام بهذين الـhelpers.
- الفرض في طبقة التطبيق الآن (الـAPI service-role) + RLS حزام أمان لاحقاً.

## 7) الفوترة تقنياً
- checkout المؤسسي على المالك.
- per-seat عبر Stripe (اشتراك بالكمية = عدد الأعضاء **المنتِجين فقط**) — **يُربط قبل الإطلاق**؛ حتى ذلك الحين لوحة المؤسسة تعرض عدد المقاعد المدفوعة والتكلفة المتوقعة.
- الأعضاء لا يمرّون على Stripe إطلاقاً.
- usage-guard يعتمد getEffectivePlan.

## 8) صفحة التسعير (إعادة صياغة)
- المؤسسي = «طبقة الإدارة» (لوحة، أقسام، رؤية شاملة، تقارير محفظة) — وليس «مخرجات غير محدودة لفرد».
- توضيح: أضف مقعداً احترافياً لكل شخص يُنتج العمل.
